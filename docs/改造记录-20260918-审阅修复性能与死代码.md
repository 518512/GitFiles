## 1. 修改了什么

### 1.1 阶段一：浏览器端仓库树缓存与刷新合并

**问题**：`js/githubdisk.js` 的 `getRepoTreeState` 声称按 HEAD 缓存，实际每次调用都发一次
完整递归树请求（`force` 参数从未被使用，`invalidateRepoTree` 只把 `disk.head` 置空）。
一次目录导航会重复拉两次，一次写操作因多次通知触发多轮刷新。

**改动**：

```text
js/githubdisk.js
  + repoTreeCache / repoTreeInflight（键 = diskId + branch）
  + readCachedRepoTree()：命中条件是「缓存 head === disk.head」
  + getRepoTreeState()：缓存命中/在途请求复用/回源后写缓存，并建立 byPath 索引
  ~ invalidateRepoTree()：只删缓存，不再清 disk.head
  ~ executeOperations()：写成功后先更新 disk.head 再失效缓存；去掉被覆盖的死赋值
  ~ getFileContentMeta(disk, path, {force})：默认走缓存并返回 updatedAt
  ~ getFileProperties()：复用 meta.updatedAt，不再单独拉一次整树
  ~ notifyListChange()：按 diskId 合并到 120ms 窗口只派发一次
```

命中条件是 `缓存.head === disk.head` 而不是把 head 放进键：首次加载时 `head` 可能为
`null`，放进键会永远 miss；写操作成功后 `disk.head` 前进，旧缓存自然失配回源。

## 2. 为什么这样改

- **树缓存是最高影响项**：它同时解释了「目录导航慢」「README 页重复请求」「一次上传触发
  多次刷新」三类现象，且 `AGENTS.md §19` 早已把它写成既有能力——属于实现与规范脱节。
- **批量上传是硬规则违反**：`AGENTS.md §3` 明确禁止「100 个文件产生 100 个 Commit」。
- **去重键的内存问题有 OOM 风险**：Worker 内存上限约 128MB，而 `join(',')` 对 25MB
  字节数组会产生约 150MB 的临时字符串；改成按长度分组 + 内容复核既省内存又不牺牲正确性。
- **删除的死代码都带「看起来还活着」的误导性**：例如假统计面板、download→upload 的旧复制
  实现、永不命中的 base64 分支——留着会误导后续维护者。

新增测试覆盖的正是本次风险最高的三处：

1. **树缓存**：连续/并发读取只发一次请求；HEAD 变化后自动回源；`invalidateRepoTree` 强制回源；
   属性面板只读一次树。这是「缓存导致读到旧树」的回归闸门。
2. **字节去重**：同长度不同内容绝不共享 Blob（防数据损坏）；同内容仍复用同一个 Blob。
3. **批量上传**：N 个文件只产生一次 `/operations`；不覆盖同名文件；超限文件如实上报且不产生 commit。

### 6.1 新发现的 bug：在已存在目录里无法新建/重命名文件

`workers/operations.js` 的 `taken()` 用「前缀集合」判断祖先是否构成冲突，而目录本身
就是一个前缀。结果：

```text
create docs/new.md            → 422 Path already exists: docs/new.md
rename docs/a.md → docs/b.md  → 422 Path already exists: docs/b.md
同一批里往同一个新目录写第 2 个文件 → 422
```

只有「顶层文件」或「写入一个全新目录」才能成功。已用 `git show HEAD:workers/operations.js`
在修改前的实现上复现确认，属于**预先存在**的问题（此前的测试只重命名根目录文件，
因此没被发现）。

修法：区分「条目（blob/gitlink，在 `nfcPaths` 里）」与「目录前缀（只在前缀计数里）」——
只有当目标的某个祖先是**条目**时才拒绝；祖先仅是目录前缀属正常。新增 3 项回归测试，
其中一项是反向用例（文件祖先仍必须阻止写入）。
