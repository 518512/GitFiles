# GitFiles 架构现状与上游关系

> 本文回答两个问题：**现在的架构是什么**，以及 **GitFiles 与上游 storage-hub 是什么关系**。
>
> 对应 `main @ d34c974`

---

## 1. 当前架构

```text
Browser / Android PWA
        │ 同源 HTTPS + HttpOnly Cookie
        ▼
Cloudflare Worker（workers/entry.js，唯一 HTTP 入口）
        │
   ┌────┴─────────────────────┐
   ▼                          ▼
  D1                       GitHub
 sessions /                OAuth（PKCE）
 repository_access              │
                                ▼
                          Git Data API
                     Blob / Tree / Commit / Ref
```

### 模块边界

```text
workers/
  entry.js                 HTTP 路由与 CORS；/api/* 与静态资源分派
  http.js                  ApiError / json / assertSameOrigin / 路由解析
  session.js               Cookie session、ACL（TTL 重校验）、过期清理
  repos.js                 仓库读取、列表、创建、文件下载入口
  operations.js            Git Data 变更管线（CAS + 批量单 commit）
  github.js                GitHub API 客户端（含流式下载）
  schema.sql               D1 表结构（幂等，可重复执行）

js/
  github-api.js            浏览器端唯一 API 客户端（只调同源 /api/*）
  githubdisk.js            GitHub storage 的 UI 与调用封装
  github-paths.js          纯路径工具
  markdown-lite.js         安全 Markdown 渲染（README 视图）
  app.js                   工作区 UI 与状态
  localdisk.js / drive.js  本地存储 / Google Drive（上游遗留）

css/
  style.css                历史基础层
  ui-v2.css                设计令牌 + V2 覆盖层（必须最后层叠）

scripts/
  build-config.mjs         汇集 public/ + 注入配置
  check-ui.mjs             UI 结构静态校验
  bump-cache.js            提升 APP_VERSION 以刷新 SW 缓存
```

### 关键不变量

| 不变量 | 实现位置 |
|---|---|
| GitHub token 永不进入浏览器 | 所有 GitHub 调用在 Worker；cookie 为 HttpOnly |
| 写操作必须 CAS | `operations.js` 重读远端 HEAD 比对 `expectedHead` |
| 批量 = 一个 Tree + 一个 Commit | `operations.js` 完整快照建 root tree |
| Move/Rename/Copy 复用 Blob SHA | `applyOperations()` 路径重写 |
| 依赖树完整快照而非 `base_tree` | 保证删除语义，`base_tree` 会让删除变 no-op |
| `/api/*` 永不缓存 | `sw.js` |
| README 渲染不可能 XSS | `markdown-lite.js` 先整体转义再白名单替换 |

## 3. 与上游的关系

### 3.1 当前状态：已脱离 fork 网络，作为独立仓库维护

2026-09-12 通过 GitHub 的 **Settings → General → Danger Zone → Leave fork network**
解除了 fork 关系。该操作**不可逆**，仓库无法再连回 fork 网络。

因此现在的定性是明确的：

> **GitFiles 是一个独立项目，源自 storage-hub。**
> 它共享 storage-hub 的 Git 历史起点，但已不隶属于 fork 网络，
> 也不再作为「上游的补丁集」维护。

解除 fork 时的实测数据（用于说明分离的合理性）：

| 指标 | 数值 |
|---|---|
| 领先上游提交 | 70 |
| 落后上游提交 | **0**（未遗漏上游任何改动） |
| merge-base | `5693a08`（= 上游 HEAD） |
| 差异规模 | 132 文件，+12001 / −3772 行 |

> 注意：`Leave fork network` 会**丢弃** issues、PR、wiki、stars、watchers 等平台数据
> （commit 历史完整保留）。若仓库有这些数据需要先备份。

### 3.2 为什么分离：代码与产品层面已不是同一个项目

这不是主观判断，而是可量化的：

- 上游**没有后端**，核心承诺是「纯客户端、不存储用户文件在开发者服务器」；
  GitFiles 引入了 Worker + D1，认证模型、信任边界、部署形态全部改变。
- 上游的数据模型是 Google Drive；GitFiles 是 Git 对象模型（Blob/Tree/Commit/Ref），
  并实现了 CAS、批量单 commit、Blob SHA 复用 —— 这些在上游都不存在。
- 上游**没有任何测试**；GitFiles 有 77 项。
- 上游没有 LICENSE，也没有 `package.json`。

上游的代码演进对这个项目已无增量价值，继续合并只会制造冲突。

### 3.3 仍需注意的边界

**上游仍是 MIT 之外的无许可状态，这是唯一的实质约束**：

| 事项 | 状态 |
|---|---|
| **LICENSE** | ⚠️ 上游未声明 LICENSE，默认保留全部权利。**取得授权前不可再分发** |
| 血缘署名 | ✅ README 顶部已设「致谢与致敬」专节，署名原作者 Mykhailo Mikus |
| `upstream` remote | 保留，仅作只读参考（禁止向上游 push / 提 PR） |
| GitHub 仓库 About / 描述 | 建议同步为独立项目定位（非 fork） |

**建议的收尾顺序**：

```text
1. 解决 LICENSE ← 唯一阻塞项
2. 加 package.json + CI（让测试成为契约）
3. 清理死代码，让代码库只包含实际生效的路径
4. 同步 GitHub 仓库 About 描述
```

### 3.4 若要继续据此派生

如果你打算基于 GitFiles 再做派生，请注意两点：

1. 本仓库同样**没有 LICENSE**，继承上游的无许可状态；
2. 上游 storage-hub 的作者署名必须保留 —— 这是 README 中「致谢与致敬」一节存在的原因。
