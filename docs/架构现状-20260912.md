# GitFiles 架构现状与上游关系

> 本文回答两个问题：**现在的架构是什么**，以及 **GitFiles 还是不是 Storage Hub 的 fork**。
>
> 对应 `main @ d34c974`

---

## 1. 当前架构

```text
Browser / Android PWA
        │ 同源 HTTPS + HttpOnly Cookie
        ▼
Cloudflare Worker（workers/entry.js，唯一 HTTP 入口）
        │
   ┌────┴─────────────────────┐
   ▼                          ▼
  D1                       GitHub
 sessions /                OAuth（PKCE）
 repository_access              │
                                ▼
                          Git Data API
                     Blob / Tree / Commit / Ref
```

### 模块边界

```text
workers/
  entry.js                 HTTP 路由与 CORS；/api/* 与静态资源分派
  http.js                  ApiError / json / assertSameOrigin / 路由解析
  session.js               Cookie session、ACL（TTL 重校验）、过期清理
  repos.js                 仓库读取、列表、创建、文件下载入口
  operations.js            Git Data 变更管线（CAS + 批量单 commit）
  github.js                GitHub API 客户端（含流式下载）
  schema.sql               D1 表结构（幂等，可重复执行）

js/
  github-api.js            浏览器端唯一 API 客户端（只调同源 /api/*）
  githubdisk.js            GitHub storage 的 UI 与调用封装
  github-paths.js          纯路径工具
  markdown-lite.js         安全 Markdown 渲染（README 视图）
  app.js                   工作区 UI 与状态
  localdisk.js / drive.js  本地存储 / Google Drive（上游遗留）

css/
  style.css                历史基础层
  ui-v2.css                设计令牌 + V2 覆盖层（必须最后层叠）

scripts/
  build-config.mjs         汇集 public/ + 注入配置
  check-ui.mjs             UI 结构静态校验
  bump-cache.js            提升 APP_VERSION 以刷新 SW 缓存
```

### 关键不变量

| 不变量 | 实现位置 |
|---|---|
| GitHub token 永不进入浏览器 | 所有 GitHub 调用在 Worker；cookie 为 HttpOnly |
| 写操作必须 CAS | `operations.js` 重读远端 HEAD 比对 `expectedHead` |
| 批量 = 一个 Tree + 一个 Commit | `operations.js` 完整快照建 root tree |
| Move/Rename/Copy 复用 Blob SHA | `applyOperations()` 路径重写 |
| 依赖树完整快照而非 `base_tree` | 保证删除语义，`base_tree` 会让删除变 no-op |
| `/api/*` 永不缓存 | `sw.js` |
| README 渲染不可能 XSS | `markdown-lite.js` 先整体转义再白名单替换 |

## 3. 结论：还算 fork 吗？

**分两个层面回答，因为答案不同。**

### 3.1 Git 层面：是 fork，而且关系是干净的

- 共享完整历史，merge-base 恰好是上游 HEAD。
- `upstream` remote 仍配置为 `fi3ik-mme/storage-hub`。
- 领先 70 个提交，**落后 0 个** —— 没有遗漏上游任何改动。
- `AGENTS.md` §33 明确：禁止向上游提 PR 或 Push，所有提交只推 `origin`。

### 3.2 代码与产品层面：已经不是同一个项目

这不是主观判断，而是可量化的：

- 上游**没有后端**，核心承诺是「纯客户端、不存储用户文件在开发者服务器」；
  GitFiles 引入了 Worker + D1，认证模型、信任边界、部署形态全部改变。
- 上游的数据模型是 Google Drive；GitFiles 是 Git 对象模型（Blob/Tree/Commit/Ref），
  并实现了 CAS、批量单 commit、Blob SHA 复用 —— 这些在上游都不存在。
- 上游**没有任何测试**；GitFiles 有 77 项。
- 上游甚至没有 LICENSE，也没有 `package.json`。

**建议的定性**：

> GitFiles 是一个**基于 Storage Hub 历史的独立产品**。它构造性地是一个 fork
> （共享历史），但已经不该按「上游的补丁集」来维护 —— 上游的代码演进对它已无
> 增量价值，继续合并上游只会制造冲突。
>
> 更贴切的说法：**GitFiles 是 Storage Hub 的一个「重度派生分支 / 独立线路」**。
> 如果希望社区把它当独立项目看待，正确的做法见 3.3。

### 3.3 如果要把「独立库」做实，需要补的东西

目前阻碍它被当作独立项目对待的，不是代码而是**工程外壳**：

| 缺失 | 影响 | 建议 |
|---|---|---|
| **LICENSE** | 上游没有 LICENSE，意味着默认保留全部权利，**法律上不可再分发**。这是最需要先解决的问题。 | 与上游作者确认授权，或取得许可后自行选定（如 MIT）；在无授权前不宜公开分发 |
| 独立仓库描述 / 定位 | 上游 README 的定位（Google Drive 为主）与实际能力不符 | 已完成（中文 README + 双语），但 GitHub 仓库 About 需同步 |
| **package.json** | 无 `npm test` 入口、无版本号、无 CI 触发约定 | 加最小 `package.json`（scripts.test / scripts.check-ui） |
| **CI** | 测试不会自动运行 | GitHub Actions：跑 `node --test` + `check-ui.mjs` |
| 版本与发布 | 无 tag、无 CHANGELOG | 按里程碑打 tag |
| 死代码 | `js/github/*`（1200 行）、`copyGithubItemToGithub`、Google Drive 兼容层 | 见 `docs/状态总览-20260912.md` P-03 |
| 上游归属说明 | 当前 README 未显著声明血缘 | 在 README 增加「基于 Storage Hub 派生」小节 |

**我的建议顺序**：

```text
1. 先解决 LICENSE（这是阻塞项，其他都可以晚）
2. 加 package.json + CI（让测试成为契约）
3. 清理死代码，让代码库只包含实际生效的路径
4. README 补血缘说明
5. 此时再考虑是否把仓库从 fork 网络里独立出来
```

> 注意：GitHub 上的「fork 标记」是平台层面的关系，与代码是否独立无关。
> 即使代码完全独立，只要仓库仍是 fork，页面就会显示 "forked from"。
> 若确实要脱离，需要联系 GitHub Support 解除 fork 网络，或新建独立仓库迁移。
> **不建议**在没有 LICENSE 的情况下贸然迁移。
