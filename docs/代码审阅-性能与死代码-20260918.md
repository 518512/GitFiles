## 1. 性能问题

### P0-1 浏览器端仓库树缓存并不存在（最高影响）

- 位置：`js/githubdisk.js:1834-1849`（`getRepoTreeState`）、`:1870`（`listFiles`）、`:1963`（`getFileContentMeta`）、`:219-224`（`invalidateRepoTree`）
- 证据：

  ```js
  // :1842 注释声称 “Cached per owner/repo/branch/head — a moved HEAD re-keys the cache.”
  async function getRepoTreeState(disk, { force = false } = {}) {
    const data = await GithubApi.request(`/api/repos/.../tree?branch=...`);  // 无任何缓存读取
  ```

  ```js
  // :219
  function invalidateRepoTree(diskId) {
    // ... no browser-side Git tree cache or credential exists to clear.
    if (disk) disk.head = null;
  }
  ```

- 影响：
  - `force` 参数被完全忽略；`AGENTS.md §19` 与状态总览声称的「按 `owner/repo/branch/head` 作键的 Tree Cache」**在代码中不存在**，只剩失效钩子。
  - Worker 侧每个 `/tree` = 2 次上游调用（`workers/repos.js:43` 递归树 + `:47` 取 commit 日期）。
  - 一次目录导航 = 2 次全量树：`app.js:2698` `listFiles` + `app.js:2768` `syncTreeWithCurrentPath` → `loadTreeChildren`（`app.js:2080` 再次 `listFiles`）。逐层深入 d 层 = `2(1+d)` 次全量树。
  - `getFileContentMeta`（`:1963`）为查**一个文件**的 SHA/size 也拉整棵树；保存文件（`:777`）、打开文件（`:2072`）、属性面板（`:2344` + `:2358` 共 2 次）、深链解析（`:2417` + `:2427` 最多再 4 次重试）都在重复付费。
- 建议：在 `githubdisk.js` 内建 `Map<owner/repo/branch/head, {tree, treeSha, updatedAt, byPath}>`，`force` 时穿透，`invalidateRepoTree` 只删该 key（不要再把 `disk.head` 置空，见 P0-4）；同时用 in-flight Promise 合并并发同 key 请求。风险：低（读路径，服务端 CAS 仍是权威）。

### P0-2 一次写操作触发多次全量刷新（通知风暴）

- 位置：`js/githubdisk.js:96-98`（`notifyListChange`）、`:307`、`:333`、`:1007`；监听器 `js/app.js:3553-3556`
- 证据：

  ```js
  function notifyListChange(diskId) { listChangeListener?.(diskId); }   // 同步、不 await
  ```

  ```js
  GithubDisk.setListChangeListener((diskId) => {
    if (...) refreshGithubFolderView({ reloadTree: true, silent: true });  // 每次通知 = 一次刷新
  });
  ```

- 影响：`notifyListChange` 全文件 20 处调用；一次上传会经 `addPending`(307) → `resolvePending`(333) → 函数尾(1007) 通知 3 次。每次刷新都会 `clearTreeCache` + 重走 `syncTreeWithCurrentPath`，即每文件操作约 6 次全量树请求。
- 建议：在 `notifyListChange` 内按 `diskId` 合并（`Set` + `queueMicrotask`/`rAF` 只派发一次）。风险：低（纯 UI 节流，不碰写语义）。

### P0-3 多文件上传逐文件一个 commit（违反 AGENTS §3）

- 位置：`js/app.js:1658-1681`（`uploadFilesToCurrentFolder` 循环 `await GithubDisk.createFileFromBlob`）
- 影响：100 个文件 = 100 个 Tree + 100 个 Commit；每个文件还前置一次取 HEAD 的整树请求与 3 次刷新通知。客户端已有 `executeBatch`（`githubdisk.js:2283`）可做到「一次 Tree + 一次 Commit」。
- 建议：先收集内容与失败项 → 组装 `create` 操作数组 → 一次 `executeBatch`；单文件错误单独回报。风险：中（需保留错误可见性与大小校验）。

### P0-4 写操作前用整棵树换 `expectedHead`，且随后被置空

- 位置：`js/githubdisk.js:173`、`:187-188`、`:219-224`
- 证据：

  ```js
  if (!disk.head) await getRepoTreeState(disk, { force: true });   // :173 为拿 HEAD 拉整树
  ...
  disk.head = result.head;      // :187
  invalidateRepoTree(diskId);   // :188 → 内部 disk.head = null，:187 是死赋值
  ```

- 影响：每次写入固定多付「全量树 + commit」两次上游调用，只为填 CAS 基线；`:187` 赋值立即被覆盖。
- 建议：保留 `result.head`；`invalidateRepoTree` 只清树缓存。更彻底可加一个只返回 commit SHA 的轻量 ref 端点（需同步 `AGENTS.md §12` 路由表）。风险：中低。

### P1-5 搜索框无防抖 + 每个文件项挂 ~14 个监听器

- 位置：`js/app.js:3311`（input）→ `:1882`（`renderCurrentView`）→ `:1283`/`:1312`（全量重建）；逐项监听 `:406-460`（contextmenu/more-btn/touch×4/click）+ `:3065-3116`（drag×5）
- 影响：每敲一个字符 `innerHTML=''` 重建列表，每项约 14 个监听器；200 项目录 ≈ 2800 监听器/击键，移动端单次 50–200ms，输入 10 字符即 10 次。
- 建议：input 加 ~120ms 防抖（或 rAF 合并）；容器级事件委托（`closest('[data-id]')` / `closest('.item-more-btn')`）把监听器从 O(n) 降到 O(1)。风险：低。

### P1-6 `updateProgressBars` 每 250ms 做 O(n²) 查找

- 位置：`js/app.js:1127-1135`，定时器 `:1154-1161`
- 证据：

  ```js
  document.querySelectorAll('.file-item[data-id], .list-row[data-id]').forEach((el) => {
    const file = state.files.find((entry) => entry.id === el.dataset.id);
  ```

- 影响：500 项 × 每 250ms = 每秒约 100 万次比较，且进度期间持续数分钟。
- 建议：渲染时建 `Map<id, file>`，查找降为 O(1)。风险：低。

### P1-7 `escapeHtml` 走 DOM 往返

- 位置：`js/app.js:1345-1349`、`js/contextmenu.js:1644-1648`
- 证据：

  ```js
  function escapeHtml(str) { const div = document.createElement('div'); div.textContent = str; return div.innerHTML; }
  ```

- 影响：每个文件行调用 2–4 次（名称、aria-label、状态、图标），200 项 ≈ 600+ 次 DOM 元素创建/销毁。
- 建议：改为对 `&<>"'` 的一次正则替换（或复用同一个 `div`）。**不得**放宽转义字符集（AGENTS §17）。风险：低。

### P1-8 `refreshUserQuotas` 每次导航重算全部配额

- 位置：`js/app.js:793-830`，调用点 `:2740/:2761/:2770/:2802`
- 影响：每个已挂载 GitHub 仓库发一次 `/api/repos/:owner/:repo`（`githubdisk.js:2369`）；每个本地盘做一次 IndexedDB 全表 `getAll`（`localdisk.js:224`），且 `getAllocatableSize` 内 `navigator.storage.estimate()` 被调用两遍（`localdisk.js:264-270`）。配额只是侧栏一个文本标签。
- 建议：加 TTL（如 60s）缓存，仅在有缓存缺失时补齐；写成功后主动失效。风险：低。

### P1-9 Worker `applyOperations` 每个操作都全量重建索引

- 位置：`workers/operations.js:213-217`（`reindex`）与 `:268`（每次操作后调用）
- 证据：

  ```js
  const reindex = () => {
    prefixes = buildPrefixIndex(index);
    nfcPaths = new Map([...index.keys()].map((path) => [path.normalize('NFC'), path]));
    nfcPrefixes = new Set([...prefixes].map((prefix) => prefix.normalize('NFC')));
  };
  ...
  for (const op of operations) { ...; reindex(); }   // O(ops × entries)
  ```

- 影响：1000 个操作 × 1 万条目 ≈ 千万级迭代 + 每轮两次全量 Map/Set 构造与 NFC 归一化，直接消耗 Worker CPU 预算（免费档 10ms）。
- 建议：只在受影响的前缀上增量更新，或整批结束后统一 `reindex()` 一次（`taken` 判断可在批内用局部集合）。风险：中（需保持批内顺序语义与现有测试）。

### P1-10 Worker `contentKeyOf` 把二进制数组 `join` 成字符串

- 位置：`workers/operations.js:98-100`
- 证据：

  ```js
  return typeof content === 'string' ? `text:${content}` : `bytes:${content.join(',')}`;
  ```

- 影响：25MB 字节数组 → 约 7500 万字符的临时字符串（UTF-16 约 150MB），而 Worker 内存上限约 128MB，存在 OOM 风险；同时 `Array.from` + JSON 序列化本身已放大约 3.6 倍（见 P2-15）。
- 建议：改为长度 + 内容哈希（或对字节数组不做内容级去重）。风险：低（去重是优化，不是正确性）。

### P1-11 Worker `/api/repos?refresh=1` 串行 N 次 D1 写

- 位置：`workers/repos.js:145-154`
- 证据：

  ```js
  for (const repo of shaped) { await upsertAclRow(env, { ... }); }   // 最多 1000 次串行 await
  ```

- 影响：最多 10 页 × 100 = 1000 个仓库，每个一次 D1 往返；`connectExistingRepository`（`githubdisk.js:1514`）总是强制刷新，故这是常用路径。
- 建议：用 `env.DB.batch([...])` 一次提交（D1 支持批量预处理语句）。风险：低。

### P2-12 记事本：光标状态、查找、撤销栈

- `js/notepad.js:1046-1055`：`updateCaretStatus` 每次 `input/click/keyup/select/scroll` 都 `text.slice(0,pos).split('\n')`；1MB 文本每次按键分配 1MB。改 `lastIndexOf('\n', pos-1)` 计数即可。
- `js/notepad.js:867/918/930/943`：一次「查找下一个」把全文匹配位置重算 3 次（`findNext` → `selectMatchAt` → `updateFindStatus`）。
- `js/notepad.js:26-32/719-757`：`editHistory` 保存整篇文本快照、`maxSize: 100` 且无大小上限 → 5MB 文件最多约 500MB 常驻内存（Android 首要目标，易 OOM）。建议按文档大小动态降级 `maxSize`。

### P2-13 本地磁盘递归操作每层全量读盘

- 位置：`js/localdisk.js:606-631`（`:623` 每层 `getAllEntries`）、`:284-295`（`putEntry` 每次写要 `getEntry` + `checkDiskQuota`→`getDiskUsage`→`getAllEntries` + 写，3 次 IDB 往返）
- 影响：复制 100 个文件夹、整盘 1000 条 ≈ 10 万次条目读。
- 建议：单次递归内一次性读盘并按 `parentId` 建 Map；批量删除/回收放进一个 `readwrite` 事务；配额增量在内存累加。

### P2-14 `githubdisk.js` 内部线性扫描

- `:311-348` `findPendingEntry`/`resolvePending`/`failPending` 遍历 `pendingByFolder` 全表 → 同目录 N 个文件上传 O(N²)（N=200 ≈ 2 万次 `findIndex`）。建议加 `Map<tempId, {key, entry}>` 索引。
- `:65-85` + `:381-403` `findActiveMoveForPath` 对每个文件扫描全部 move 状态（O(F×M)）且每次新建数组。建议 `Map<diskId, Map<sourcePath, state>>` + 逐级前缀回溯。
- `:886-907` `mergePendingFiles` 连续 4 次 `files.map`，`getPendingEntries` 每渲染取 2 次副本。建议合并为单次循环 + 末尾一次排序。

### P2-15 客户端二进制序列化：`Uint8Array` → 数字数组

- 位置：`js/githubdisk.js:158-163`（`serializeOperations` 的 `Array.from`）、`:1984`（`assertUploadSize` 上限 100MB）
- 影响：25MB 二进制 → 2500 万元素数组 + 约 3.6 倍 JSON，而 Worker 上限是 **25MB**（`workers/operations.js:5`）。超限文件要整包上传后才收到 422，前后端上限不一致。
- 建议：客户端直接发 base64 字符串（Worker `encodeContent` 内部本就转 base64），并把客户端上限对齐 25MB。风险：中（需同步改 Worker）。

### P2-16 CSS 中作用于 layout 的过渡

- `css/style.css:3578`：`transition: width .15s ease, flex-basis .15s ease;` + `:3580` 折叠改 `width/flex-basis` → 每帧重算 flex 容器与 `.content` 宽度。建议改 `transform: translateX(-100%)`。
- `css/style.css:929`：进度条 `transition: width 0.2s linear;`（由 `app.js:1099` 内联宽度驱动）。建议 `transform: scaleX()` + `transform-origin: left`。

### P3-17 Worker 树条目排序可省

- 位置：`workers/operations.js:348` `entries.sort((a, b) => a.path.localeCompare(b.path))`
- 说明：GitHub 建 tree 时会自行排序，客户端排序不影响结果；`localeCompare` 走 ICU collation，明显慢于普通比较。可去掉或换简单比较。风险：低。
